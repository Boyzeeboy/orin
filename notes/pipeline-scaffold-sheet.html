Internal runbook · pipeline repo

Standing up a new client's token pipeline

The producer side of a Build — everything that has to exist before client-site-setup-sheet can begin. Drafted from the Synthesis scaffold and then corrected by walking it end to end on the Onkey clone, which is where four of the six steps turned out to be wrong or missing.

The rule

One clone per client, scaffolded once. A fresh clone of the baseline, not a fork and not a branch.

Scaffolding is a day-one act. Re-running it on a live pipeline resets the snapshot and the changelog, which is how a client's token history disappears.

Day one · six steps
1Clone

A fresh clone of the baseline. It ships as projectName: "Unconfigured" with prefix tok.

git clone <baseline> {client}-token-pipeline
Fresh clone
2Scaffold

Run it with --dry-run first: it prints every change and writes nothing. Then drop the flag.

npm run scaffold-client -- \
  --name "Acme" --prefix acme \
  --figma-name "Acme DS" \
  --figma-key AbC123 --dry-run
quote any value with a space
Rehearse, then apply
3Build, then commit

The scaffold clears dist/. Build before committing, or the commit holds a dist/ no fresh build reproduces.

npm install && npm test
git checkout -b chore/scaffold-{client}
Source and dist together
4Install the plugin

The scaffold made a new plugin — new name, new id, new port. Figma has never seen it.

Figma → Plugins → Development →
Import plugin from manifest…
{client}-token-pipeline/plugin/manifest.json
Or there is nothing to press
5First sync

Sink first, then Sync in the plugin. Expect a very large diff: the seed fixture against a real system.

npm run sink
npm run sync:figma -- --dry-run
Read the audit
6Settle the red

A fresh config declares no mode-parity exceptions, so a real system usually fails the first build. Judge each one, declare it with a reason.

npm run sync:figma && npm test
modeParity.expectedIdentical
Day one ends green
What scaffold-client rewrites five steps in its header, eight files on disk
pipeline.config.mjs ← the client's values package.json ← name, version 0.1.0 dist/{light,dark}/ cleared tokens/snapshot.json reset to {} tokens/changelog.json reset to [] plugin/manifest.json ← name, id, sink port plugin/ui.html ← default port CLAUDE.md / AGENTS.md ← regenerated
It does not touch tokens/*.json

The seed fixture stays until the first Figma sync overwrites it, so the repo builds green immediately. That is what step 3 is proving.

The counts differ by one between runs: --dry-run lists the docs regeneration as a change, the real run does it and does not list it. Nine reported, eight reported, same work.

The flags four required, the rest optional
▲--name"Acme" — display name, and the plugin's suffix
▲--prefixacme → --acme-colour-…
▲--figma-nameexact file name. Provenance matches on it
▲--figma-keyfrom the file URL. Recorded, never resolved
△--sink-portdefault 9231. Must be 9224–9232
△--sitepath to their app, or the site checks skip
△--scope@acme → @acme/tokens, else acme-tokens
A missing required flag exits 1 before anything is written

--help prints the usage block. --author and --repo set package.json identity and are worth passing if the repo already exists.

Known failure modes · learned the hard way
Scaffolding twice

It resets snapshot.json and changelog.json unconditionally. On a live pipeline that erases the client's token history while leaving the tokens themselves in place, so nothing looks wrong. Scaffold once, on day one, and never again.

The scaffold sits uncommitted

Synthesis was scaffolded and first-synced on 3–4 August and committed on the 19th. For a fortnight the only record of it was a dirty working tree, and a sync:figma without --dry-run would have overwritten it with nothing to return to. Commit the scaffold before the first sync, then the sync separately.

npm's echo makes a quoted value look split

npm re-prints the command without quotes, so --figma-name "Acme DS" renders as --figma-name Acme DS. Your shell quoting worked; copying that echoed line would not. It sets the file name to the first word, scaffolds happily, and surfaces much later as a provenance refusal.

The first sync diff looks catastrophic

Expect four figures. The seed fixture is a few dozen tokens and a real system is several hundred, so the first sync reports the whole difference: one Onkey run showed 1145 changes, with names restructuring as colour/action/primary became colour/action/primary/DEFAULT. Nothing is lost; read the collection audit and the provenance line, not the change count.

A port outside 9224–9232

The script refuses it, correctly: the plugin manifest's devAllowedDomains covers only that range, so a port outside it would import fine and fail at request time, which is a worse way to find out.

Two clients on the same port

The default is 9231 for everyone. Give each client a different one, or two sinks can both be listening and a payload lands in the wrong repo. The provenance check catches it — but a caught error is still an error, and the port is the cheaper fix.

The Figma file name is not exact

Provenance compares strings with no trimming and no case folding. You only reliably know the name after fetching once, so the honest order is scaffold with your best guess, fetch, then correct figmaFileName from what the dump reports.

Their Figma does not follow the convention

The step-5 audit will say so, by name. Fix it by renaming in Figma wherever possible. An override in the figma block is the fallback and a standing record that their file diverges, so it should feel slightly worse than renaming.

Cutting the first release

Nothing reaches their app until a tag exists and they pin to it. Semver here is written for tokens, not for code.

MAJOR

A token renamed or removed, or a shipped value changed shape. An existing var() stops resolving.

MINOR

Tokens added, or a new mode. Existing names keep their meaning.

PATCH

A value changed within its existing name and type. A brand colour moving two shades is a PATCH, however loud it looks.

Bump package.json before cutting the tag

Tag annotated, with the reasoning in the message. npm run tag does it. Never move a published tag: consumers cache them, so a moved tag means two people have different code under one name. Bump their pin separately, and only when you mean to.

The scaffold is deliberately unpolished

Its own header says so: nobody operates this pipeline without me in the room, so it does not need to survive a stranger holding it wrong. That is a scope decision, not an oversight — and it is why this sheet exists rather than a friendlier script.

When that stops being true, the script needs hardening before this sheet needs expanding.

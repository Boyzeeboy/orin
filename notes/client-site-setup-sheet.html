Internal runbook · site repo

Wiring a new client site to the token pipeline

The consumer side of a Build. Assumes the pipeline repo is already scaffolded and tagged. Modelled on the KR site — the worked example — with the seams it closed in July already accounted for.

The rule

All token changes start in Figma, never in code. The site consumes; it never authors.

A value the site needs but the tokens don't have is a token proposal — authored at the source, then pinned and pulled. Never a literal in styles.css.

The pipeline repo's CI skips the contract when the site is absent — which is always. The strongest check only really runs from this side.

Known failure modes · learned the hard way
The contract silently skips

It's the strongest check in the system, and it no-ops when the site repo isn't present. In pipeline-only CI it never runs. Wire it into the site's CI on day one.

A floating pin isn't a pin

A tag pin gives rollback and an audit trail. Point at a branch and you've rebuilt the sibling-path problem with extra steps.

The vendor file gets hand-edited

Twice in KR a generated file was edited and silently overwritten on next sync. If a value looks wrong, fix it in Figma — the fix must survive the rebuild.

Dark is built but never shipped

The pipeline gates both modes; sync copies light only. Either wire data-theme consumption or stop gating dark. Don't leave it half-live.

Docs assert what the system knows

Every doc failure in KR was a fact a machine could answer — a count, a command, a version. If the system can answer it, the doc must not assert it.

Colours with no token

Expect a handful in any real site — KR had six, incl. a navy spanning contact, thank-you and the email templates. Log them; they're a palette decision, not engineering.

Taking an upgrade

Tokens change in Figma → the pipeline lands it through its gated PR flow → version bumped and tagged. Nothing reaches the site until the pin is bumped here, deliberately. Semver is written for tokens, not code:

MAJOR

A token is removed, renamed, or changes meaning — an existing var() in the site stops resolving.

MINOR

Tokens added, or a new mode. Nothing existing breaks.

PATCH

A value retuned, or a build/doc fix. Visual change possible; contract unaffected.

Bump, sync, run the contract, then look at it

A MAJOR is the only one that can break the build — but a PATCH can still change how the site looks. The contract proves it resolves, not that it's right.

The site is a consumer. Keep it that way.

Every seam above exists to stop one thing: a value reaching the page without passing through the token layer. The transport is pinned so it can't drift, the vendor file is generated so it can't be edited, the contract runs here so it can't skip.

Nobody operates this without you in the room — the setup is commoditised, the design judgement is not.

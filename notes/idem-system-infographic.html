From Figma to the app

IDEM is designed in one Figma file and installed by an app as one package. Between them sit two layers: a token pipeline that turns design decisions into values, and a component layer that turns those values into React. Above them, pages build the design's screens from the package alone, the canvas shows all of it beside Figma, and every component has a page of its own that says how to use it. Everything flows one way, and a check stands at every handover.

The rule

Figma → token files → dist/ → components → the package → the app.

A fix is made at the layer that owns it, never downstream, so the next sync can't undo it. A design fault is fixed in Figma, then synced.

The system at a glance

Four stops. The first is where design decisions are made, the middle two are this repository, and the last is whoever installs @boyzeeboy/idem-ui. Today that's examples/web, a stand-in for the IDEM app that the consumer check installs on every pull request.

Beside the four stops: pages, the canvas and component pages.

A page is one of the design's screens built from the package exactly as an app would build it, held to its Figma screen by a contract, and never shipped. The canvas frames every story beside its Figma source and its drift. All three are in the repository, and all three are checked.

Layer one: the token pipeline

A token is a named design decision, such as "the primary button's background", with a value per mode. The pipeline's job is to carry those names and values out of Figma without anyone retyping them, and to refuse anything it can't trust.

01 Export figma-console's figma_export_tokens writes tokens/.figma-dump.json straight to disk. The plugin is restarted first because the export reads its cache, not the live file (ORIN-75). Figma
02 npm run sync:figma Writes all four token files the build reads, so none is edited by hand: tokens/tokens.{light,dark}.json from Primitives, Semantic and Components, aliases kept, and size.json and typography.json from Fonts, Spacing and Radius, values resolved (ORIN-119). Refuses a dump that's stale, from another file, alias-resolved or missing a collection; --expect refuses one that lacks the change you just made. Each sync stamps tokens/figma-sync.json, which a daily check compares with Figma. Gate
03 Token files W3C DTCG, aliases kept, so a semantic token still points at its primitive. The source of truth on the code side, committed and reviewed as a diff. Two tiers below components: primitives (teal/500) are never used directly; semantic tokens (colour/action/primary) are. Source

Then it snapshots the result into tokens/changelog.json and, when a shipped token changed, writes a changeset: patch for a value, minor for an addition, major for a removal. Gate

Layer two: what a contract carries

Above the components: pages

A page is one of the design's screens built only from the package, as an app would build it. It lives in src/pages, is held to its Figma screen by a contract of "kind": "page", and never ships. PROCESS.md Step 10.

What makes it a page
  • The same machinery. A Figma screen is a component, so the ready check, the read and --init work on it unchanged. Its parts are the screen's regions; composes is the components it places.
  • Views are variants. The Images screen's Grid and List frames are one set, View=Grid|List, and its View button switches the page between them.
  • Built from the entry. Check 7 fails a page that imports a component's own files, or that a package export names.
  • Compared by the numbers. Each region's position and size, read from Figma and from the page. Grid matches to the pixel; List is 2px off, because Table's border is drawn outside its rows (ORIN-104).
What a page has found
  • Layout the components didn't need. The Images screen had 15 unbound gaps, three hidden leftovers and a library fill, all fixed in Figma first.
  • Values no component owned. The table's column widths were numbers in the design; they're table/* tokens now, applied by <Table layout="batch">.
  • A gap in the ready check. It read a component's own size, not its children's; it reports unbound child widths now.
  • Bugs in shipped components. Button dropped a passed className; Checkbox drew mixed as empty for a frame in production. Both fixed and released.
The checks, and what each one proves

Each check compares two things and catches a different failure. The point is the seams between them: a component can name the right tokens and still be unreadable, or render perfectly and still not be the component the design drew.

01 test:sync · verify The pipeline's own logic, and that every output exists in both modes. Every token path names exactly the CSS variable the build emits. npm test
02 verify:contracts Contract against code, in eight checks. The schema holds, every named token is emitted in both modes, no primitives, contrast passes on text and non-text pairs, every story exists, no literal hex or px, the CSS uses no token its contract doesn't list, every composed component is rendered, no stray inline SVG, a page builds only from the package, and every declared behaviour has a play test tagged with it. npm test
03 Storybook tests Renders every story, runs axe on it in light and dark, and runs its play test: a menu closes on Escape, Select All goes mixed. The contract decides which play tests must exist. The only check that proves the result is usable rather than merely well-named: the first round of required tests found Left Navigation's account menu out of the tab order (fixed in 1.20.3). npm test
04 Screenshots On every pull request, each story's full page compared with its committed baseline, failing on more than 10 changed pixels. Baselines are made by labelling the PR update-screenshots and reviewed as images in the diff. This replaced Chromatic, whose runs on main are now skipped. CI
05 test:consumer The package as an app gets it. Packs the tarball, installs it into a copy of examples/web outside the repo, resolves every export, typechecks and builds it, then opens it in Chromium with Playwright and confirms each component's computed style equals its token in both themes. npm test · CI
06 verify:canvas Every story a contract lists is framed, every framed component has a Figma source or is marked code-authored, the canvas has no literals, and every frame's drift is recorded. npm test
07 verify:pages Every component has its page in both views, every guidance section is written, every component, token and story a page links to exists, the built pages are current, and a component whose code changed has a changeset that names it. npm test
08 verify:canvas-a11y The canvas is hand-written, with no contract, so it gets its own audit: axe on its front page, the Images page and a component page of each kind (with Figma or code-authored, with parts or none, the icon set, drifted), in both themes, with contrast checked with the frames hidden (ORIN-118). npm test
09 Figma changes A sync only happens when someone runs it. Every morning a workflow compares Figma's version history with tokens/figma-sync.json and opens an issue if the file has changed since the last sync (ORIN-120). It can't see which variables changed, so the issue means run the sync and see. CI · daily
10 verify:figma Contract against design. Reads every component and page in Figma and reports every property where the design binds a different token from the contract, and writes the verdict to canvas/drift.json. On demand, because it needs a live read of Figma. On demand

Component pages: one specification, two views

Every component has a page: on the canvas for designers, and as its docs page in Storybook for developers. Both read the same generated data, so they can't disagree. Almost all of it is generated from what's already kept and checked; only the guidance is written. PROCESS.md Step 11.

Generated
  • Header. The component's description from its code, its Figma source and drift, and the package version.
  • Anatomy, tokens and sizes. Its parts, and every token it uses in both modes, read from the build.
  • Accessibility. The contract's a11y, with each contrast pair measured.
  • Code. Its exports and props, read from the source.
  • History. Its changelog entries, the contract at each release, and its token changes.
Written, and checked
  • Guidance. A file per component: use it for, don't use it for, behaviour, content, composition, and do and don't pairs. All 40 are written.
  • Examples are stories. Each do and don't is a story rendered on the page, never a drawing, so it shows the shipped component.
  • Storybook around it. A Getting started page from the README, a playground per component with live controls, the version in the sidebar, and the changelog (ORIN-107 to 111).
When the design changes
Case A · the value changes

The designer makes the button less round by repointing button/radius. The component still binds button/radius, so no code changes.

edit in Figma → sync → build → npm test → release

The app gets a patch release and a new corner. This is what the component tier of tokens is for, and it should be the common case.

Case B · the binding changes

The designer points the button at a different token. That's a re-specification, so verify:figma fails, names the property on both sides, and the canvas marks the frame drifted.

verify:figma fails → talk → --fix the contract → update CSS → npm test

The conversation is the point, and can't be automated. Frequent Case B means the token layer is missing a component token.

What the app gets, and what it never does
The package carries
  • 40 components, from the root or one entry each: @boyzeeboy/idem-ui/button.
  • One stylesheet, tokens.css: both modes, dark switched on by a .dark class or data-theme="dark".
  • Tokens on their own for anything the components don't cover: light.css, dark.css, and JS and JSON forms.
  • Icons and the logo, drawn in currentColor, so they take the colour around them.
  • Types, so props are checked in the app's editor.
  • A version, through changesets, so a design change arrives as an upgrade the app chooses to take.
The app never
  • Hardcodes a value. No hex, px or font names; if a token is missing, it's added in Figma. Not even a table's column widths: layout="batch".
  • Uses a primitive. Colours come through semantic or component tokens.
  • Edits the package. A fix in the app is undone by the next release. It goes back to its source layer.
  • Restyles a component's tokens. A different look is a new variant, designed in Figma.

One direction, and every handover checked

Nothing in this system generates the design from code or pushes code into Figma. A design change never reaches the app on its own: it travels through a sync, a build, a set of checks and a release, and each of those can stop it and say why.

When a check finds the design at fault, the fix is made in Figma, as the layer that owns it, and synced like any other change: a value bound, a frame named, a contrast pair corrected. That's the rule working, not an exception to it.

What that buys the app is the right to trust a version number. If @boyzeeboy/idem-ui installs and renders, it matches the design it was built from.

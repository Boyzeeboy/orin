Everything from the Foundation, in one page. Your shadcn components are untouched — what changed is where their values come from. Keep this where you'd find it in six months, which is when you'll want it.

The one rule

Change values in the token source. Never in globals.css.

That file is now generated. Editing it works right up until the next build, then silently reverts — which is worse than it not working at all.

Changing your brand colour · the whole job
1 — edit the source

Find the value by its role. Change it. This is the only file you touch.

// tokens/src/semantic.json
"primary": {
  "$value": "{teal.500}" "{indigo.500}"
}

Then run npm run tokens and commit what changes. That's it — both themes, every component, one edit.

2 — what gets written for you

Your globals.css, regenerated. Two shapes, depending on your Tailwind version — yours is whichever I set up.

Tailwind v4 
/* generated — do not edit */
@theme inline {
  --color-primary: var(--primary);
}
:root  { --primary: oklch(.51 .09 195); }
.dark  { --primary: oklch(.78 .07 195); }
Tailwind v3 
/* generated — do not edit */
:root  { --primary: 189 100% 26%; }
.dark  { --primary: 186 39% 68%; }
/* tailwind.config.js reads these via
   hsl(var(--primary)) — also generated */
What's yours to edit, and what isn't
Yours — compose freely
✓Every component in components/ui/ — they're yours, as shadcn intends. Change them.
✓Your pages, layouts, routes and logic. The tokens constrain values, not decisions.
✓Tailwind classes in your markup — p-4, flex, rounded-md and the rest.
✓tokens/src/*.json — the source. Change values here as often as you like.
Generated — edits here vanish
✕app/globals.css — rewritten on every build. It carries a "do not edit" header for this reason.
✕The theme block in tailwind.config.js (v3 only) — also generated.
✕Anything with /* generated */ at the top. If in doubt, look at the first line.
Hardcoding a colour fails the build

A raw hex or a one-off size in a component is caught before it ships. Not to be strict — because that's the exact thing that makes a rebrand expensive later.

When something goes red
What you'll seeWhat it means, and what to do
A hardcoded value was found Someone typed a colour or size straight into a component. Swap it for the token that means the same thing. If nothing does, that's a real gap — add it to the source, or send it to me.
A token isn't defined Your CSS refers to something the source doesn't contain — usually a typo, or a name that changed. Check the spelling against the token file first.
shadcn references --something; the build doesn't define it A name one of your shadcn components expects isn't in the token source. Read this one carefully, because it's the only failure here that would otherwise be invisible: nothing errors, the variable is simply unset, so that element renders transparent or inherits whatever sits behind it. It can look very nearly right until a customer finds the screen where it doesn't. Usually it means a component was added after the set was built. Add the missing name to the source, or send it to me.
Dark mode looks wrong Most often a value that's identical in both themes when it shouldn't be. The build flags these, but it can't know which are deliberate — a transparent border legitimately matches. Read the list rather than waving it through.
The build passes but it looks off The checks prove every value resolves, not that it's the right one. If you changed a token, this is just the change reaching everywhere it should.
A change didn't appear Nine times out of ten the build wasn't re-run, or globals.css was edited directly and then regenerated over. Run npm run tokens and check the diff.
Two layers, and which one to use
Build from roles, not from the raw scale

The source has two layers. The raw scale is the palette itself: every shade, every step, named for what it is. The roles sit on top and say what each one is for — the page background, the primary action, the body text colour. Your components read the roles. Only the roles.

Reaching past a role to grab a raw value works perfectly, which is the whole problem: it resolves today and it looks right today. But the raw scale is the part that moves when your brand changes, and anything reading it directly moves with it, unasked and unreviewed. A role survives a rebrand because a rebrand is a change to what the role points at. That is the entire reason the two layers exist, and it is invisible until the day it costs you.

On your setup this is a convention, not a check. The guardrail catches a colour typed straight into a component, but it can't yet tell a role from a raw value once both are proper tokens. So this one is on you and me rather than on the build. If you're unsure which layer a name belongs to, ask — that question is cheap and the wrong answer is quiet.

When you need a value that doesn't exist
Add it to the source, not the component

It'll happen — a screen needs a shade or a size the set doesn't have. The instinct to resist is typing it into the component, because that always feels faster and the build will stop you anyway.

Add it where the others live, give it a name that describes its job rather than its appearance — surface-raised, not light-grey-2 — then rebuild. A name about appearance is a lie waiting to happen at the next rebrand.

And when you're not sure

Adding a value is easy. Deciding whether it should exist is the part worth pausing on — most "I need a new grey" moments are really an existing one used slightly wrong.

Send me the screen and what you tried. That question is exactly what the retainer is for, and it's cheaper than a set that quietly grows to forty greys nobody can tell apart.

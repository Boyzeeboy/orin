The Orin Token Pipeline

Figma authors the value. Code consumes it.
One route between them, with a gate on the end of it.

The promise

A design system that exists in your codebase, not in a Figma file your developers translate by hand. Every value travels one way, and a red check stops a broken one shipping.

A fresh read

The plugin dumps the Figma file again. Values and descriptions, in one request.

Compared with the repo

Diffed against tokens/*.json. Nothing is written, in either direction.

Non-zero on any disagreement

It names exactly what moved, and it runs on demand: a live read needs a person at Figma.

Where Figma authors

A failure means the repo is stale, and the answer is to sync. That is the direction this pipeline ships in.

Where code authors and Figma mirrors

A failure means somebody edited a generated file. That is a defect, not a sync.

Deliberately outside npm test

The check needs a dump only a human at Figma can produce. Wired into CI it would fail every run on a stale dump rather than on real drift, which teaches everyone to ignore it.

What this gives you

Consistency

One value, one place. The product cannot quietly disagree with the design file.

Efficiency

No manual exports. Nobody copies a hex out of a Figma panel into a stylesheet.

Reliability

A broken alias, a stale vendor file, a name that swallowed its siblings: each has a check.

Scalability

Both modes build from the same source, so dark mode is authored rather than retrofitted.

Developer-ready

CSS custom properties, ES modules and flat JSON. No framework to adopt.

Only author in Figma

tokens/, dist/ and the app's vendor file are all downstream. A fix made in one of them is reverted by the next sync, silently, which is the failure this pipeline exists to prevent.

Why it's locked

Each rule closes a route by which a value could reach the product without passing through a token. Break one and drift becomes possible again, silently.

Nine of the ten can fail the build

The colour audit is informational by design: a hex matching a token's value does not make that token the right one. npm run build keeps the report advisory so you can build in order to look at a problem; npm test runs it strict, and that is what decides whether anything ships.

One command per client

npm run scaffold-client writes the client's name, token prefix, Figma file and sink port, then regenerates the router from the template. Standing this up is setup, not a build.

Decide it once, in Figma. Ship it everywhere.

The pipeline commoditises setup, never design judgement. If it starts shipping opinions about which tokens should exist, it has drifted.

What it does own is the boring part: the route from a brand decision to a shipped surface, and the checks that stop that route quietly breaking.

Read alongside "How this site is built". That sheet diagrams the Orin site, where JSON authors and Figma mirrors. This one diagrams the baseline that is for sale, where Figma authors and code consumes. Same shape, opposite direction of truth, and the difference is deliberate: the site is designed in the browser with no Figma round-trip, which is not how a design team with a variables file works.

Two things this pipeline has that the site does not. CI (.github/workflows/ci.yml runs npm test on every PR to main, then checks a fresh build reproduces the committed dist/), and a second repo: the pipeline publishes, the app consumes and pins a tag. dist/report.html is untracked on purpose, because its content depends on whether a consuming app is checked out alongside.

Names above are illustrative. A fresh clone of the baseline ships as projectName: "Unconfigured" with prefix tok; the client's real values arrive at scaffold, which is why the router carrying them is generated rather than written. The Figma plugin posts to a loopback port on the operator's machine, so nothing leaves it.

Colour, type, spacing and radius above are Orin's own tokens, transcribed from tokens/src/. This is a standalone artefact: it does not read vendor/tokens.css and is not covered by npm test. --family-mono still has no token, as flagged on the setup sheet; the gap is open rather than conditional.

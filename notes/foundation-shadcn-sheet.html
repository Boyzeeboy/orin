Being fair to shadcn

I build on shadcn rather than replacing it. It got the hard part right — the names describe roles, not colours, which is the thing most teams never do. The gap is one level up.

What it already gives you

Genuinely useful. Keep all of it.
  • ✓Semantic variables — --background, --primary, --border. Named by job, not by shade.
  • ✓A dark block layered over the top, so theming is possible from day one.
  • ✓Components you own outright, in your repo. No dependency to escape later.
  • ✓Sensible defaults that get a product in front of people fast.

What it hasn't got

The four things this fortnight installs.
  • +An authored source. Somewhere the values are decided, above the CSS file.
  • +A build. Something that turns that source into the code, rather than a person retyping it.
  • +Both themes, resolved. Dark built from the same source and checked, rather than a second copy kept by hand that drifts out of step with the first.
  • +A guardrail. A check that fails when someone bypasses the system — because someone will.

Today — values typed inline

/* globals.css — hand-edited */
:root {
  --primary: 173 100% 26%;
  --background: 0 0% 96%;
}
.dark {
  --primary: 181 39% 64%;
  --background: 194 42% 11%;
}

You have the names without the ownership. Nothing sits above this file, so changing your brand means editing it — and every place someone typed a value directly instead.

After — the same file, generated

/* generated — do not edit */
:root {
  --primary: 173 100% 26%;
  --background: 0 0% 96%;
}
/* ↑ built from your token source
   ↑ dark resolved and checked
   ↑ regenerated, never retyped */

Same file, same shadcn components, nothing to relearn. The difference is that this file is now an output — so there's one place to change a colour, and it's upstream.

Being straight about the limits
It won't make the product well designed

It makes it consistent, and cheap to change. Someone still has to decide what good looks like — that's the Build, or it's you.

It's worth less if nothing will change

The test is how many people will change this after I leave, times how often. Two people shipping a frozen app for a year? Wait.

It needs one habit kept

Values get decided upstream, not typed into a component. The guardrail catches slips — but a team routing around it gets friction, not benefit.

The cheapest time to do this is before there's much to convert.

Right now you have a handful of components and one developer. The conversion is two weeks and nothing has to freeze. That is the whole argument — and it stops being true fairly quickly.

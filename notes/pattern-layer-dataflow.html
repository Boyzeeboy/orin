What actually moves

Values travel a one-way pipe, from a variable in Figma to a var() in a stylesheet. Component structure never travels at all. It gets emitted on one side, written by hand on the other, and compared. Two different shapes, one Figma file.

The short answer

Nothing in here generates component code, and nothing builds page layouts.

The value layer is a pipeline. The pattern layer is a comparison. They look alike on a diagram and behave nothing alike.

1 · The value path, stage by stage Built and running

Six stages, each one derived from the stage before it. That is what makes the whole thing checkable: at every point there is a right answer, and a script can ask for it.

2 · The same token, at every stage Built and running

One colour, five shapes. Worth reading top to bottom once, because most confusion about this pipeline is really confusion about which of these five things someone means when they say "the token".

In Figmaa Variable
colour/text/primary  (Semantic collection)
Light → alias to neutral/900  ·  Dark → alias to neutral/50 A decision about where a value belongs, pointing at a primitive that holds the value.
In the dumpa positional tuple
["colour/text/primary", 1, 0, "#1f343a", "#f4f5f5"] Name, collection index, type index, then one resolved value per mode in that collection's mode order. Compact because a full dump exceeds the tool's response cap.
In tokens.light.jsonDTCG
"primary": { "$type": "color", "$value": "#1f343a",
  "$description": "Purpose: … Usage: … Guidelines: …" } The description rides along from Figma. It is the only usage guidance the tokens carry, and the report is where anyone actually reads it.
In dista CSS custom property
--kr-colour-text-primary: #1f343a; Prefixed per client so two token packages can load on one page without colliding.
In the sitea reference
color: var(--kr-colour-text-primary); Write the hex here instead and the build goes red. That is the whole value layer, in one sentence.
3 · What reads the flow, and where it stops it Built and running

A gate is a thing that reads the pipe and refuses. These run locally on npm test, which is deliberate: protection is local, and every one of them was added after something got through.

provenance The sync refuses a dump whose Figma file name is not the configured one. Two pipelines checked out at once cannot cross-contaminate, whatever port they share. Gate
freshness A dump older than 15 minutes is a snapshot, not a reading. check:figma refuses to compare against it, and the hash catches a dump edited by hand after the sink wrote it. Gate
extraction parity The plugin and the paste-in snippet do the same job by two routes. Both run against one mock and their output must match exactly. The snippet is the one piece that cannot otherwise be tested. Gate
verify-build All six dist outputs exist and are non-empty. Cheap, and it catches a build that half-failed. Gate
mode-parity Fails when a semantic colour resolves identically in both modes, which is the signature of broken alias resolution. Exceptions are declared one by one with a reason, never by regex. Gate
semantic-only The site must not reach past the semantic layer into primitives. Easy to violate invisibly, by aliasing a primitive to a friendly local name, which is exactly why it needs a check and not a convention. Gate
hardcoded, sync, contract No raw hex or font-family in the surface; dist and the site's vendor file identical; every token the site references actually defined. Gate
verify-docs Every npm script, file path and report check id the prose names is real. It cannot verify that prose is wise, only that the things it names exist. That gap is the whole argument for the layer below. Referential
4 · The second path, and where it stops Parked, nothing adopted

Same Figma file, different objects. Component sets rather than variables, and structure rather than values. Notice that it does not reach the site: this path has no destination, it has a counterparty.

1Extract

A second reader

componentPropertyDefinitions

Variant property names, their allowed values, defaults. The API surface, and only that.

Not the node tree, so not composition. "An icon above a heading above one button" is not in here.

Structure, not values
2Emit

The contract

dist/contract.json

Not through Style Dictionary. That builds token trees, and component structure is not a token.

Generated from the source it describes, so it cannot drift from the system it claims to document.

Never hand-written
3Compare

The diff

contract-parity

A new report check, diffing what design says the API is against what the code says it is.

Skips honestly when there is no code side, because a skip states plainly that nothing was proven.

The gate
The contract covers the API surface. It does not cover composition.

Which means the proposal's "Built from" field, the one that claims a new pattern composes only locked primitives, has no automatic check behind it. Someone asserts it. The gate is narrower than the mechanism sheet implies, and that is worth knowing before anyone pays for it.

5 · Code Connect runs the other way Parked, nothing adopted

This is the part that reads backwards. Code Connect does not generate code from Figma, and it does not push components into a repo. It is a mapping file, written by hand in the code repo, published upward so a developer inspecting the Figma component sees the real code instead of Figma's generated approximation.

Figma component set

Variant properties and their allowed values.

Button · variant, size, state
published up
Code Connect

Hand-authored. An assertion that these two things correspond.

Button.figma.ts
describes
The code component

Props, variants, defaults. The truth on the code side.

Button.tsx
So the diff has three parties, not two.

The contract says what design thinks the API is. Code Connect says what the code claims it is. The component itself is what the code actually does.

And the middle one is written by hand, so it can be wrong.

A red contract-parity proves design and the mapping disagree. It does not prove which is right, and it cannot see a mapping that lies about the component behind it.

6 · The only loop in the whole system Parked, nothing adopted

Everything above is a line. This is the one cycle, and it is the third option the mechanism sheet is about: what happens when the contract has no answer.

01 Read

The agent checks the contract for a pattern that fits. Nothing matches.

02 Propose

A record carrying Gap, Built from, Why not X, and the counter at used in: 0/2. Captured now, not remembered later.

03 Build anyway

From locked primitives, so the code is token-correct even while the pattern is not yet canonical. Nothing is blocked.

04 Graduate

Second genuine use takes the counter to 2/2. A person builds the real component, in Figma.

And the loop closes at the top of band 1. The graduated component appears in the next extraction like anything else, which is the reason a proposals/ folder in the repo was rejected: staging a pattern as a committed code artefact reintroduces the code-side authoring this pipeline exists to prevent.

The counter needs a physical home in Figma, and that is still undecided.

The component description field is the only durable free-text surface the plugin already reads. Plugin data is the other candidate. The graduation check cannot be built until someone picks one.

A pipeline and a diff are not the same instrument

Bands 1 to 3 can be checked end to end, because every stage is derived from the one before it. Ask whether dist matches source and there is a right answer sitting there waiting.

A diff cannot work that way. Both sides are authored by different people in different tools. When the check goes red it tells you they disagree; it cannot tell you which one is wrong, and someone has to go and look.

That is a weaker gate for more machinery, and it is the honest reason this waits for a trigger rather than getting built because the diagram looks tidy.

Handover · for your developers

Your design system, in your codebase

Your tokens now live in your own repositories and ship from your own pipeline. This is the short version of how to use them, what not to touch, and what to do when something goes red.

The one rule

Values are authored in Figma, never in code. Your site reads them; it doesn't define them.

That single rule is what stops your codebase and your designs drifting apart. Everything else here exists to make it easy to keep.

You bump the version, run the sync, and your CI confirms every token the site uses still exists.

Your call
Upgrades are never automatic

Your site is pinned to an exact version. A design change can't surprise you in production — you take it deliberately, and you can roll back to the previous tag at any time.

Using the tokens
Use the semantic layer

Semantic tokens describe a role — what the value is for. They're the layer you build with, and the only layer that's safe to depend on. 

/* yes — describes the role */
color: var(--{prefix}-colour-text-default);
background: var(--{prefix}-colour-background-raised);
padding: var(--{prefix}-space-6);
border-radius: var(--{prefix}-radius-md);

/* no — a raw value, invisible to the system */
color: #1f343a;

/* no — a primitive; it can be re-pointed
   under you without warning */
color: var(--{prefix}-neutral-900);
What not to edit

Two files in your site repo are generated. They're overwritten on every sync, so an edit there is lost silently — and quietly reintroduces drift.

✕vendor/tokens.css — generated from the release. If a value looks wrong, it's a Figma change, not a file edit.
✕Anything under node_modules/ — replaced on every install.
✓styles.css and your components — yours. Compose freely, using the tokens.
✓Layout, structure, content, behaviour — all yours. The tokens constrain values, not decisions.
When a check goes red
What you'll seeWhat it means, and what to do
A token isn't defined Your CSS references a var(--{prefix}-…) the released tokens don't contain — usually a typo, or a token that was renamed in a major version. Check the spelling against the token report first; if it's genuinely gone, the release notes will say what replaced it.
A hardcoded value was found A colour, size or font slipped into the CSS directly. This one is listed rather than failed — a hex often matches several tokens by coincidence, so the report can't tell you which was meant. Swap it for the semantic token that means the same thing. If nothing means the same thing, that's a gap worth telling me about — see below.
A primitive is being consumed Something in the CSS reads a raw scale value rather than a role — the difference shown above. It resolves today, which is why this is a check and not a bug you'd notice: primitives get re-pointed when the palette moves, and anything reading one directly moves with it, unasked. Find the semantic token for the job it's doing. If none exists, that's the same gap as the row above and worth sending to me.
Sync is out of date The committed vendor/tokens.css doesn't match the pinned version. Re-run the sync and commit the result. If it still differs, the file was hand-edited at some point.
The build looks fine but the page looks wrong The checks prove every token resolves — not that it's the right one. A patch release can retune a value deliberately. Compare against the release notes, and flag it if it wasn't intended.
When the system can't express what you need
Don't force it. Ask.

It will happen — a screen needs a value the tokens don't have. The two instincts to resist are hardcoding it and grabbing the nearest primitive. Both work today and both cost you later.

Send me the gap instead: where it's needed, what you tried, and what you'd call it. I'll author it in Figma, cut a release, and you bump the pin. Usually same-day.

Why it's worth the extra step

A hardcoded value doesn't appear in the design file, and won't change when the palette does. The report lists it in the colour audit, but as a prompt to look rather than a failure — nothing stops it shipping. It's how a system quietly stops being true.

One value added properly is a few minutes. Forty added informally is a system nobody trusts — which is the state most teams call me in to fix.

Systems decay quietly. That's the part to watch.

Nothing here breaks loudly. It erodes — a hardcoded value here, a skipped sync there, until the design file and the codebase describe two different products. The checks catch most of it. The rest is a habit worth keeping.
